# Learnings

## Codebase Patterns

- The extension uses Mocha + `@vscode/test-electron`. Tests live in `src/test/suite/*.test.ts` and are discovered by `src/test/suite/index.ts` via a glob over compiled `.test.js` files in `dist/test`. `npm test` runs `pretest` (which calls `tsc`) and then `node ./dist/test/runTest.js`. Running the suite locally requires an X server — under headless devcontainers, prefix the run with `Xvfb :99 -screen 0 1280x1024x24 &` and `DISPLAY=:99`. `xvfb-run` itself is unavailable because `xauth` is not installed.
- The orchestrator pattern: `promptAndRunReset(outputChannel)` walks the user through the pickers and then calls `runReset(mode, scope, outputChannel, options?)`. The orchestrator (`runReset`) is the unit-testable seam — tests drive it directly with explicit `(mode, scope)` pairs instead of trying to puppeteer the QuickPick UI. Slice 2 added the optional `RunResetOptions.confirmer` parameter as the dependency-injection seam for the modal confirmation dialog; the picker stays in the driver layer because Slice 4's preview must reuse the same `runReset` without re-prompting through the picker.
- Every reset invocation returns a `ResetInvocationRecord` capturing `timestamp`, `mode`, `scope`, `keysConsidered`, `keysChanged`, `commands` (each a `CommandStepResult` with success/error), and `failures`. `formatInvocationLog` and `summariseInvocation` are pure functions over the record so they are testable without VS Code in the loop. Future slices append to the same record shape; do not invent parallel result types.
- Side-effectful sub-steps are funnelled through `executeVSCodeCommand(id)` and `updateSettingTarget(key, target, folderUri?)`, both of which never throw — failure is captured as data on the returned result. This is what makes S23 (partial-failure tolerance) safe by construction. Mirror this pattern for any new side-effectful call in future slices.
- The mode and scope picker options are exposed as the constants `MODE_OPTIONS` and `SCOPE_OPTIONS` in `src/utils/index.ts`. Tests use these constants to enforce S35 ("exactly three modes") at the source level rather than driving the QuickPick UI. Keep them as the single source of truth for labels and descriptions. The scope `label` in `SCOPE_OPTIONS` is the static, scope-only name; the user-facing label that adapts to a remote host is computed via `labelForScope(scope, remoteName)` at display time (S15).
- The activity log surface is the `Reset Sizes` Output Channel created in `extension.ts`. The Output Channel is exposed via three entry points (the `resetSizes.openActivityLog` Command Palette command, the "View log" action on the summary notification, and the `command:resetSizes.openActivityLog` markdown link inside `package.json`'s `resetSizes.showSummaryNotification.markdownDescription`). Future slices that need to reach the log reuse these entry points — do not bypass with custom panels.
- The activity log canonicalises target names (`Global`, `Workspace`, `WorkspaceFolder`) verbatim so users diffing runs can see the underlying API target. The user-facing bucket label (`bucketLabelForTarget(target, remoteName)`) — which folds `WorkspaceFolder` under `Workspace` (S6, S7) and adapts `Global` to `User settings (remote)` (S15) — is reserved for the summary notification and confirmation dialog. Both surfaces share `bucketLabelForTarget` as the single source of truth; don't re-implement the rule.
- Test suites that exercise `runReset` should silence `resetSizes.showSummaryNotification` (and disable `resetSizes.confirmBeforeDestructiveReset`) in `suiteSetup` and restore in `suiteTeardown`, otherwise every test pops a notification or a modal whose dismissal is fire-and-forget. The dedicated test for S25 toggles the silencing back inside its own `try/finally`; tests that exercise the confirmation gate inject their own confirmer via `RunResetOptions.confirmer` and assert the call/decline path.
- Tests that need a workspace-target write must run under an open workspace folder. `src/test/runTest.ts` launches the host with `launchArgs: [testWorkspace]` pointing to `test-fixtures/test-workspace/`. The fixture is tracked in git (gitignore pins the legacy `test-workspace/` to the repo root with `/test-workspace/` so nested fixture paths aren't accidentally ignored). To exercise `WorkspaceFolder` writes, use `vscode.workspace.workspaceFolders![0].uri` for the `folderUri` argument.
- Discovery (ADR 0003) lives in `src/utils/discovery.ts`. `CURATED_SIZE_KEYS` is the always-considered list. `SIZE_KEY_SUFFIXES` is the closed contract of suffix tokens (`fontSize`, `lineHeight`, `zoomLevel`) — adding/removing one is a behavioural change. `isSizeFamilyKey(key)` is the single source of truth for the in-family check; the `resetSizes.*` namespace is hard-excluded so the extension's own preferences are never cleared (S32). Suffix matching is **case-insensitive endswith on the full key**, which preserves `editor.tabSize` (S11) because `tabsize` doesn't end in `fontsize`.
- The cascade planner lives in `src/utils/cascade.ts`. `planCascade(scope, considered, inspect, folders)` is pure — it takes an injected `inspect` callback so the planner can be unit-tested against fake configs without VS Code. The production `inspect` is `inspectViaConfig` in `resetAllSizes.ts`, which wraps `WorkspaceConfiguration.inspect` with capture-failure-as-data. Use the same DI pattern if you need to test new cascade rules.
- **Side-effect injection seams.** `RunResetOptions` is the single point where every side-effecting UI/system call into `runReset` gets injected: `confirmer` (Slice 2, modal dialog), `reloadPrompter` (Slice 3, post-reset notification), `reloader` (Slice 3, `workbench.action.reloadWindow`). Production defaults live in `resetAllSizes.ts` and are picked up via `??` fallback. Tests inject stubs to assert the orchestrator's branching without driving the real UI; Slice 4's preview reuses the same `runReset` and gets to feed it surrogate prompts on the same seam. Whenever you add another side-effecting interaction, extend `RunResetOptions` rather than reaching into `vscode.window.*` from a new place.
- **User-facing option lists are exported constants with source-level invariants.** `MODE_OPTIONS` / `SCOPE_OPTIONS` (Slice 1) and `RELOAD_PROMPT_OPTIONS` / `RELOAD_PROMPT_BUTTON_LABELS` (Slice 3) are the single source of truth for picker copy. Tests assert "exactly N options" and exact labels at the source level rather than driving the QuickPick / notification. Mirror this pattern when adding any closed enumeration of user-facing options.
- **Pure compute first, then UI shell.** Slice 4's preview matrix lives in `src/preview/computePreviewMatrix.ts` as a pure function (`InspectFn` injected). The webview shell (`previewPanel.ts`), the renderer (`previewHtml.ts`), and the message routing (`previewMessage.ts`) are layered on top — each thin and individually testable. Tests target the pure compute and the HTML/message contracts; the webview itself only needs a couple of smoke tests to confirm the wiring. Mirror this layering when adding any further read-only surface (e.g. the Activity Bar in Slice 5 reuses the same `computePreviewMatrix`).
- **Webview button → message → `runReset` is the only action path the preview owns.** The inline script in `previewHtml.ts` posts `{type:'run-reset', mode, scope}` messages; `handlePreviewMessage` in `previewMessage.ts` validates and forwards to `runReset(mode, scope, channel)`. No per-cell shortcut, no separate confirmer, no separate reload flow — ADR 0005's "one action path" rule is enforced by code shape. `handlePreviewMessage` accepts an optional `RunResetOptions` so tests can inject surrogate confirmer / reloader stubs without driving real modals.

### Learnings for future iterations

- **Slice 2 — settings-clearing path:** the `SettingChange` shape, the `keysConsidered`/`keysChanged` fields on the record, and the `summariseInvocation` "Cleared N setting(s)" branch are already in place. The cascade implementation lands in `runReset` between the existing zoom step and `appendActivityLog`. Reuse `executeVSCodeCommand`'s capture-failure-as-data pattern when invoking `WorkspaceConfiguration.update` — wrap it in an equivalent `updateSettingTarget(key, target)` helper that returns a `SettingChange`. Do not throw.
- **Confirmation gate (Slice 2):** the setting `resetSizes.confirmBeforeDestructiveReset` is already declared with `default: true`. The gate is inserted in `runReset` after discovery and before any write — the picker should not own that responsibility, since Slice 4's preview will reuse `runReset` and must hit the same gate (S29).
- **Reload prompt (Slice 3):** there is currently no reload code anywhere in the extension; S22 is satisfied by construction. Slice 3 introduces the reload-classification map and the post-reset prompt; it should sit *after* `appendActivityLog` and *before* the summary notification fires, so the summary can report "a reload occurred" when one did.
- **Tests need an X server.** The provided devcontainer ships `Xvfb` but lacks `xauth`, so `xvfb-run` errors. Start the server directly: `Xvfb :99 -screen 0 1280x1024x24 &; DISPLAY=:99 npm test`. Kill `Xvfb` and remove `/tmp/.X99-lock` afterwards to avoid lock conflicts on rerun.
- **Test-host disposable warnings.** Output channels created inside test bodies trigger `DisposableStore that has already been disposed of` warnings as the host shuts down. They are not fatal and the exit code is 0; do not chase them. If a future test fails, look at the assertion line, not the trailing warnings.

- `src/commands/resetAllSizes.ts` — wired the cascade. `runReset` now accepts an optional `RunResetOptions.confirmer` for test/preview injection. ### Learnings for future iterations

- **Slice 3 — reload prompt placement.** The reload-classification map should land alongside the cascade planner (e.g. `src/utils/reloadClassification.ts`) and be consumed inside `runReset` *after* `appendActivityLog` and *before* the summary notification. The summary notification can then report "a reload occurred" because the reload flow precedes it in code order. The memento for "reload silently" is the only piece of extension-owned persisted state and should be passed into `runReset` via the same `RunResetOptions` pattern as the confirmer.
- **Slice 4 — preview reuse.** `runReset` already accepts `RunResetOptions`; Slice 4's preview can call it directly. The preview's "what would change" computation is exactly `planCascade(scope, discoverCandidateKeys(getConfiguration()), inspectViaConfig, workspaceFolders)` — same building blocks; no writes. Be aware: `planCascade` is pure and so suitable for the preview's read-only render; the same plan is then used by the action button's `runReset` call. Do not duplicate the discovery+cascade logic into the preview surface.
- **VS Code accepts arbitrary keys at workspace scope.** The S10 end-to-end test writes `fakeThirdParty.editor.fontSize` via `WorkspaceConfiguration.update(key, value, ConfigurationTarget.Workspace)` even though no extension has declared that key in its schema. VS Code persists it to `.vscode/settings.json` and `inspect(key).workspaceValue` returns it. Subsequent `update(key, undefined, Workspace)` removes it. Useful for testing third-party-shaped discovery without installing a fake extension.
- **`Object.keys()` on `getConfiguration()` is undocumented.** The discovery walk relies on `WorkspaceConfiguration` exposing its keys as enumerable own properties. The S10 test confirms this works in VS Code 1.120; if a future slice reports keys missing from discovery in a real workspace, the proxy enumeration is the suspect.
- **Activity log target names vs. summary labels.** `formatInvocationLog` (the log surface) prints raw target names: `Global`, `Workspace`, `WorkspaceFolder`. `summariseInvocation` and `buildConfirmationMessage` (the user surfaces) use `bucketLabelForTarget` which folds WorkspaceFolder into "Workspace" (S6, S7) and swaps Global for "User settings (remote)" when remoteName is set (S15). Keep this asymmetry: the log is diagnostic, the summary is UX.
- **`keysConsidered` filtering.** `discoverCandidateKeys` returns a search universe (curated + every suffix-matched key in the resolved tree). After planning, `runReset` filters suffix-matched candidates to those that actually landed in the plan (i.e. are set at a targeted rung) before recording them in `keysConsidered`. Curated keys are always kept. This matches the Contract invariant's "suffix-matched keys present in the user's configuration at the targeted scopes" wording.
- **Discovery does not currently see WorkspaceFolder-only third-party keys at Global scope.** If a key is set only at a folder override and discovery runs at Global, `getConfiguration()` (no resource) still resolves it via cascade, so it appears in the tree. Verified in S7 testing. If a future bug surfaces here, check whether `WorkspaceConfiguration` proxy semantics changed across VS Code versions.

## Slice 3: Reload prompt with three options + silent-reload preference

### Files changed

- `package.json` — added the third extension preference `resetSizes.reloadSilently` (boolean, default `false`). Discoverable on the settings page; toggling it off restores the prompt branch (S19's reversibility requirement). Storing the silent-reload preference in `WorkspaceConfiguration` rather than a separate `Memento` keeps the surface flat — there is one source of truth, and S32's `resetSizes.*` exclusion in discovery already guarantees the preference cannot be cleared by a Global reset.
- `src/types/index.ts` — extended `ExtensionConfig` with `reloadSilently`. Added `ReloadOutcome` (`'not-required' | 'prompted-deferred' | 'reloaded'`) and the required `reloadOutcome` field on `ResetInvocationRecord` so the log, summary, and tests have one place to look up what the reload flow did per invocation.
- `src/utils/reloadClassification.ts` — new. `RELOAD_REQUIRED_KEYS: ReadonlySet<string>` (currently `{ 'window.zoomLevel' }`) and `requiresReload(key)`. Conservative by design: only `window.zoomLevel` is known to require a reload in VS Code 1.74+; every other size-family key (curated or suffix-matched) defaults to "no reload". A spurious reload prompt is more disruptive than a missed one (the user can reload manually from the Command Palette if a change appears stuck). Adding or removing an entry is a behavioural change to S16's prompt frequency.
- `src/utils/index.ts` — re-exports `RELOAD_REQUIRED_KEYS` and `requiresReload`. `getExtensionConfig` now reads `reloadSilently`. `summariseInvocation` appends `"Window reloaded"` to its parts list when `record.reloadOutcome === 'reloaded'` (S21: "the summary reports that a reload occurred"). `formatInvocationLog` appends a `Reload: <outcome>` line so the activity log records every invocation's reload outcome — the log is the durable diagnostic record.
- `src/commands/resetAllSizes.ts` — extended `RunResetOptions` with `reloadPrompter` and `reloader` injection seams (mirroring the existing `confirmer` pattern). Added the `handleReloadFlow` helper, which sits after `appendActivityLog` is initialised but before `appendActivityLog` writes (so the record's `reloadOutcome` is set before the log is written) and before `showSummaryIfEnabled` (so the summary text can name the reload). Added `RELOAD_PROMPT_OPTIONS` and `RELOAD_PROMPT_BUTTON_LABELS` as exported constants — single source of truth for the three S16 labels. Default reloader executes `workbench.action.reloadWindow` (never invoked by tests). Default prompter joins keys with `• ` bullets in a single sentence (newlines collapse unpredictably in VS Code's non-modal notifications across versions).
- `src/test/suite/reloadClassification.test.ts` — new. Pure unit tests asserting `window.zoomLevel` is reload-required, every other curated key is live, third-party suffix-matched keys default to live, and the set is non-empty (guard against accidental classification erasure breaking S16-S19).
- `src/test/suite/resetAllSizes.test.ts` — added the Slice 3 suites covering S16 (prompter fires with key list), S17 (defer leaves window + preference alone), S18 (Reload now reloads + persists nothing), S19 (Reload-silent reloads + persists at Global; reversibility), S20 (silent-reload on but no reload-requiring change → no reload), S21 (silent-reload on + reload-requiring change → silent reload + "Window reloaded" in summary), S22 (live-only resets never prompt), failed-clear interaction, dismissal path, and activity-log surfacing. The source-level S16 invariant suite asserts `RELOAD_PROMPT_BUTTON_LABELS.length === 3` and the exact wording — same pattern as S35's `MODE_OPTIONS.length === 3`.
- `src/test/suite/extension.test.ts` — manifest-level assertion that `resetSizes.reloadSilently` is declared (boolean, default `false`) so the settings page exposes the toggle (S19 reversibility).
- `src/test/suite/types.test.ts` — updated to include `reloadSilently` in the `ExtensionConfig` literal and `reloadOutcome` in the `ResetInvocationRecord` literal.
- `src/test/suite/utils.test.ts` — every existing `ResetInvocationRecord` literal now sets `reloadOutcome: 'not-required'`; no behavioural assertions changed.

### Learnings for future iterations

- **Slice 4 — preview's "what would reload" cell.** The preview can show, for each (mode, scope) cell, both the keys that would be cleared (from `planCascade`) and whether running that cell would trigger a reload. The classifier is `requiresReload(key)`; the rule is `plan.some(s => requiresReload(s.key))`. Same pure functions, no I/O, no writes.
- **`workbench.action.reloadWindow` is async-but-never-returns.** When the production reloader fires, the awaited promise never resolves because the extension host is torn down before VS Code completes the command. Don't try to chain anything after the reload — by the time you'd care, the world is being rebuilt. The `defaultReloader` carries a code comment to this effect.
- **`showInformationMessage` newlines are unreliable.** Non-modal notifications collapse `\n` in some VS Code versions. The Slice 3 reload prompt deliberately joins keys with `  • ` bullets in a single sentence rather than line breaks; the visual result is consistent across builds.
- **The reload prompt is non-modal by design** (no `{ modal: true }`), unlike the Slice 2 confirmation dialog. The confirmation is destructive-action-gating and demands a foreground decision; the reload prompt is informational follow-up after the work is done. Don't confuse the two patterns.
- **Reload decision uses only successful `keysChanged`.** A failed clear of `window.zoomLevel` does not require a reload — nothing changed. The filter `keysChanged.filter(c => c.success && requiresReload(c.key))` is what makes S22 hold by construction even when a write rejects.
- **`reloadOutcome` defaults to `'not-required'`** on every record at construction time and is updated by `handleReloadFlow`. If a future code path ever bypasses the reload flow (e.g. the cancellation path through the confirmation gate), the record's outcome stays `'not-required'`, which is the correct UX answer for "no work was done".
- **Persisting the silent-reload preference uses Global target.** S19 says "reversible from the extension's settings" — writing to Workspace would make the preference inconsistent across workspaces. The write is wrapped in a try/catch that swallows failures: if the preference can't be persisted, the user still gets reloaded (per their explicit choice) and the prompt will come back next time. Better than refusing to reload.

Pure exported function `computePreviewMatrix(rootConfig, inspect, folders, remoteName)` returning a 3 × 3 `PreviewMatrix` whose cells carry `{plan, zoomCommands, requiresReload, scopeLabel}`. Reuses `discoverCandidateKeys`, `planCascade`, `requiresReload`, `labelForScope`, `ZOOM_RESET_COMMANDS` — no new discovery/cascade logic; the preview and the action share their answer to "what would happen?" by sharing the same building blocks (ADR 0005 consequence).

### Learnings for future iterations

- **`vscode.window.showInformationMessage({modal:true})` refuses to render in the test host.** Slice 2 worked around this by injecting a `confirmer` through `RunResetOptions`. Slice 4 needed to expose the same seam via `handlePreviewMessage` — adding an optional `runResetOptions: RunResetOptions = {}` parameter forwarded straight to `runReset`. The third argument is purely a test affordance; production wires nothing through it. Use this pattern for any future surface that wraps `runReset` and needs to be testable headlessly.
- **Webview HTML is most testable when the renderer is a pure function.** `renderPreviewHtml(matrix, cspSource, nonce)` takes everything it needs as arguments and returns a string. Tests assert by substring + regex; no DOM, no `JSDOM`, no `puppeteer`. The webview panel itself becomes a thin shell that exists only to wire VS Code events to the renderer.
- **HTML-escape every user-influenced string in the rendered HTML.** Third-party extensions can contribute settings whose keys contain HTML metacharacters (`<`, `>`, `&`, `'`, `"`). The `escapeHtml` helper covers all five; the test `HTML-escapes key names so a hostile key cannot break the page` verifies the path. Without escaping, a malicious key name could break the layout or, with `enableScripts: true`, execute script.
- **CSP nonce + inline `<script>` is the simplest path for VS Code webview button → message wiring.** No bundler, no separate asset, no `localResourceRoots` plumbing. Generate a fresh 32-char nonce per render (`Math.random`-derived is fine — this is a freshness guard for our own script, not an adversary-grade token); reference it both in the `<script nonce="…">` tag and in the CSP `script-src 'nonce-…'`.
- **`onDidChangeViewState` is the natural refresh trigger.** Refreshing the panel HTML every time the webview becomes visible (instead of polling or pushing) means the matrix is always fresh against current state when the user looks at it, but never re-renders while the user can't see it. Combined with `onDidChangeConfiguration`, this covers the "what if the user edits settings in another tab?" case.
- **`retainContextWhenHidden: false` keeps memory bounded.** The webview is cheap to re-render (curated list size + folder count = small bound). There is no need to keep the webview's process alive when the user navigates away. The full re-render on becoming visible again is fast (~milliseconds).
- **Singleton webview state lives at module scope.** A single `let currentPanel: vscode.WebviewPanel | undefined` in `previewPanel.ts` is reused across invocations of `openPreviewPanel`. `panel.onDidDispose` clears the singleton so subsequent invocations create a fresh panel. The `_testGetCurrentPanel` / `_testResetCurrentPanel` exports are pure test affordances — production code never reads them.
- **The S28 (zero writes) test snapshots inspect values, not the full settings.json.** VS Code may touch unrelated state on its own during a test run (window/editor caches, etc.); the contract is "no writes from the preview opening / closing / refreshing", which is what we assert by snapshotting the specific keys (and the extension's own preferences) before/after.
- **Slice 5 — Activity Bar reuses `openPreviewPanel`.** The Activity Bar view contribution in Slice 5 should not own a separate webview; it should invoke `openPreviewPanel(context, outputChannel)` so the preview lives in exactly one place. The icon's visibility is gated by `resetSizes.showInActivityBar` via a `when` clause bound to a context key set in `activate()` based on the setting. Reuse `_testGetCurrentPanel` to verify the icon click reveals (rather than duplicates) the existing panel.
- **`event.affectsConfiguration` should be scoped, not global.** The preview's refresh listener watches namespaces that could affect the matrix: `resetSizes`, `editor`, `terminal`, `window`, `notebook`, `debug`, `markdown`, `scm`, `chat`. Watching every change would refresh on unrelated edits (e.g. `workbench.colorTheme`); watching only these namespaces avoids the storm without missing relevant changes.
- **View visibility gated by `when: "config.<setting>"`, not a custom context key.** Slice 5 contributes an Activity Bar view whose visibility is bound directly to `config.resetSizes.showInActivityBar` in the manifest. The workbench re-evaluates this without activating the extension, so a fresh install (with no `onStartupFinished` event) honours the default-off setting (S30). A custom context key would have required `setContext` from `activate()` plus a configuration listener — but our `activationEvents` are all on-demand, so the extension wouldn't be active before the user clicked the icon, and the context key would never be set. The `config.X` clause sidesteps the chicken-and-egg entirely.

### Learnings for future iterations

- **`viewsContainers.activitybar[].icon` accepts a file path, not a codicon reference.** The advisor's initial suggestion of `$(symbol-ruler)` does not work for the Activity Bar container icon — VS Code's manifest schema only accepts an SVG path (optionally with `light`/`dark` colour theme variants). Codicons are accepted in `commands[].icon` and in `views[].icon` (sidebar item icons) but NOT in activity bar containers. We ship an inline SVG; using `fill="currentColor"` lets VS Code theme it.
- **`when: "config.<setting>"` evaluates before activation.** The workbench reads view declarations from `package.json` and evaluates their `when` clauses against the configuration store without activating the contributing extension. This is the load-bearing reason Slice 5 honours the contract invariant "no startup activation cost" while still showing/hiding the icon as the setting changes: the extension is only activated when the user clicks the icon (via `onView:`), never just because the setting was toggled.
- **`WebviewViewProvider` ≠ `WebviewPanel`.** They share `webview` API surface but have different lifetimes and parent objects. Activity Bar views are `WebviewView`s (hosted in sidebar slots); Slice 4's Preview is a `WebviewPanel` (a top-level editor pane). Slice 5 builds a `WebviewViewProvider` that **delegates** to `openPreviewPanel` rather than re-implementing the matrix in the sidebar — there is exactly one Preview surface in the extension.
- **`resolveWebviewView` fires on every visibility transition when `retainContextWhenHidden: false`.** Hiding the sidebar disposes the webview; showing it again re-resolves. Means our "open the panel on resolve" path runs more than once across a user session, and the singleton in `previewPanel.ts` becomes load-bearing: the second resolve reveals the existing panel rather than opening a duplicate.
- **Testing a `WebviewViewProvider` does not require driving the real Activity Bar.** A test instantiates the provider directly, hands it a fake `WebviewView` (just enough surface — `webview.options`, `webview.html`, `onDidReceiveMessage`), and asserts the resulting effects (`_testGetCurrentPanel` returns a panel). VS Code's `vscode.window.registerWebviewViewProvider` is not exercised; the meaningful path is the `resolveWebviewView` method, which is a plain method call. Mirror this seam if a future slice adds another sidebar webview.
- **`onView:<viewId>` is necessary for the provider to register in time.** Without it, the extension never activates when the user clicks the icon, and `resolveWebviewView` cannot fire because no provider is registered for that view id. Pair every Activity Bar / sidebar view contribution with a matching `onView:` activation event.
- **Cosmetic `DisposableStore` warnings during tests are still benign.** The same warnings noted in Slice 1's learnings reappear when Slice 5's integration tests create output channels inside test bodies. They do not affect the exit code; do not chase them.
